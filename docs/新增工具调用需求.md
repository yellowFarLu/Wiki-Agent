## 业界方案调研结论

任务型对话（TOD）的标准范式是 **意图识别（Intent Detection）+ 槽位填充（Slot Filling）+ 缺失槽澄清（Clarification）**，业界有四种主流做法：

1. **单节点 Prompt 方案**：一次 LLM 调用同时输出意图和槽位 JSON，配 Few-Shot。适合意图 ≤5 个，成本低、延迟低（腾讯云 NLU 总结）。
2. **意图节点与槽位节点分离**：先分类、再按意图走专属抽槽节点。适合 5–15 个意图，延迟翻倍（约 5s）。
3. **意图 RAG 召回**：把多样化说法/多轮 Case 入向量库，检索 Few-Shot，适合成百上千意图和方言长尾。
4. **神经符号 ReAct（如 Amazon 的 ReacTOD，2026）**：意图分类和槽位解析都作为工具调用包在有界 ReAct 环里，**确定性校验器**硬保证槽位合法才能结束，自纠错率 93.1%。

业界共识原则：**结构化 JSON 输出、schema 驱动槽位、确定性校验在代码层而非只靠 Prompt、置信度阈值触发澄清、多轮上下文消解指代（“那个单号”）**。本需求只有 4 个意图且数据 Mock，方案 1 的形态 + 方案 4 的“代码层确定性校验”原则最匹配，无需上意图 RAG。

## 执行形态：3 个方案

你已选择工具纳入 PERO 治理，下面 3 个方案的差异在于**业务意图执行时用多少 Agent 自主性**：

### 方案 A：确定性业务流程（BusinessTaskFlow）+ PERO 治理过的工具（推荐）

LLM 只做一件事：输出 `{intent, confidence, slots, reason}`。之后全流程由 Java 确定性状态机驱动：

```text
CLASSIFY（LLM）→ 合并 Redis 对话状态 → 校验槽位
  → 缺槽：slot_request 事件追问，结束本轮
  → 槽齐：ToolPermissionRegistry.denyReason() 过权限
        → 工具分派（Mock）→ 格式化结果 → 清状态
```

- **优点**：可回放、可审计，符合你们现有「LLM 只判不裁、确定性程序与模型判断分离」的原则（#14）；无 API Key 时意图识别失败自动降级知识问答，Mock 工具零依赖可测；token 成本最低。
- **缺点**：流程固定，新增意图要加代码分支（但只有 4 个意图，YAGNI）。
- 工具虽注册在 PERO 治理体系，但不跑 ReAct 循环——由确定性代码经权限注册中心调用，权限拒绝同样写 TOOL_DENIED 审计。

### 方案 B：业务意图直接进 PERO ReAct 大循环

3 个工具注册后，让 PERO Agent 自主思考决定调哪个工具、缺参数时自己追问。

- **优点**：最"Agentic"，天然支持复杂组合（查完订单查轨迹）。
- **缺点**：不确定、不可回放，与你们「确定性分离」原则冲突；每轮 ReAct ≤8 次 LLM 调用，成本和延迟高；槽位追问质量依赖模型，测试困难。

### 方案 C：A 为主，预留 B 的升级口（折中）

同 A，但工具分派抽象成 `BusinessToolDispatcher` 接口，将来某意图需要多步自主规划时，可把该意图单独切到 PERO ReAct，其余仍走确定性流程。

- 实质上是 A + 一个接口边界，几乎不增加成本，却避免未来重构。

# 技术设计 · §1 总体架构：有界神经符号 ReAct（Bounded Neuro-Symbolic ReAct）

## 核心思想：自主在环内，裁决在环外

方案 B 的自主性和方案 A 的确定性不是二选一。切分原则是：

- **环内（LLM 自主）**：思考什么、选哪个工具、何时追问、何时结束——由 ReAct 模型自主决策，支持查完订单再查轨迹这类自然组合；
- **环边界（确定性硬闸，Java 代码）**：LLM 的每个提议（意图/槽位/工具调用/结论）必须通过校验器才能生效，**LLM 只提议、代码才裁决**。模型无法绕过任何一闸产生副作用。

**2. LLM 只判不裁、#14 分离**
- LLM 可以**提议**意图、槽位值、追问文案、最终答案；但槽位是否被接受（闸B）、是否需要追问（闸C）、工具是否执行（闸A）、文件是否生成，全部由确定性代码裁决；

**3. 无 Key / 识别失败自动降级知识问答**

## 2.1 对话状态结构（Redis）


状态机（全部为代码层确定性迁移，LLM 不直接写状态）：

```text
IDLE ──分类命中业务意图──▶ IN_TASK
IN_TASK ──缺必填槽──▶ WAITING_SLOT ──回答解析入槽──▶ IN_TASK
IN_TASK ──Agent 出 FINAL──▶ DONE（清状态回 IDLE）
任意态 ──高置信意图切换──▶ IN_TASK（清空不相关槽位与证据）
WAITING_SLOT ──"不查了/换个问题"──▶ DONE/IDLE
```

## 2.2 ActGate：等待态优先解析「回答」而非重跑分类

`status=WAITING_SLOT` 时本轮**不做意图分类**（直接解决"那是/对/嗯"被当新查询的问题）：

1. 确定性取消词检测（"不查了/算了/换个问题"）→ 清状态，按普通输入走分类；
2. 按 `awaitingSlot` 用**确定性解析器**从原文抽槽（订单号正则 / 上传事件 fileId）；
3. 抽到 → 入槽并打证据 `CLARIFY_ANSWER`，续跑 ReAct；抽不到 → `clarifyMisses+1`，再次追问；**连续 2 次抽不到 → 转人工**，不无限循环。

## 2.3 槽位证据规则（SlotEvidenceValidator，硬闸）

每个必填槽必须带证据戳，三类合法证据，否则槽位强制置空：

| 证据 source | 条件 |
|---|---|
| `RAW_HIT` | 当前输入原文经确定性正则命中（不接受 LLM 转述值） |
| `CLARIFY_ANSWER` | 等待槽位态下由回答解析器从原文抽到 |
| `USER_UPLOAD` | 用户经上传控件显式上传，文件校验通过 |

即：LLM 在 Thought 里写"订单号是 SF123"但原文没有该串 → 槽位不成立，Observation 回告"缺少订单号"。**禁止默认值、禁止模型脑补**。

## 2.4 槽位定义与校验

| 意图 | 必填槽 | 确定性校验规则（Mock 口径，可配置） |
|---|---|---|
| order_query / trajectory_query | `orderNo` | 正则 `^[A-Za-z0-9]{8,20}$`（兼容顺丰 SF+12 位、菜鸟等；纯数字短于 8 位拒绝），大小写归一存大写 |
| customs_generate | `mappingExcel` | xlsx；POI 读首行必须含「小包号、大包号」两列且至少 1 行数据；不符 → 拒绝并明确提示列名要求 |

槽位在**同一任务内跨工具复用**：「查下 SF123 的订单和轨迹」第一次填的 orderNo 带证据，第二个工具直接复用，不重复追问（这是方案 B 自主组合的关键）；但 Agent 出 FINAL、状态清 DONE 后，新任务需重新提供。

## 2.5 意图切换

非等待态每轮都重新分类：新意图 `confidence ≥ 阈值（默认 0.8）` 且与当前不同 → 代码裁决切换，**丢弃只服务旧意图的槽位及证据**（如 order→customs 时 orderNo 保留与否：customs 不用订单号则清除），切换事件落 trace 与 V24。低于阈值则维持当前意图，防止一句话造成抖动。

## 一、为什么用独立 key，而不是复用现有短期记忆 key

现有 [RedisShortTermMemoryAdapter](file:///Users/huangyuan/Desktop/AI学习/wiki-Agent/src/main/java/com/wikiagent/infrastructure/memory/redis/RedisShortTermMemoryAdapter.java) 的 key `wikiagent:memory:{userId}:{sessionId}` 存的是 **Redis List（逐轮 append 的原始消息流水）**，而对话状态需要的是**单个可变 JSON 对象**。二者无法共用一个 key，根因是数据形态和写入语义不同：

| 维度 | 短期记忆（List） | 对话状态（JSON 对象） |
|---|---|---|
| 数据形态 | 多条不可变消息，RPUSH 追加 | 单对象，跨轮原地改写（槽位填充/意图切换） |
| 维护操作 | 超限 LTRIM 裁剪 | 读—改—写整体覆盖 + version CAS |
| 语义 | 原始对话记录（**证据**，不能改） | 派生出的机器状态（可丢弃、可重建） |
| 消费方 | 所有链路（PERO/RAG/网关） | 仅业务意图网关 |

如果硬塞进 List（比如追加一条"状态消息"），会出现三个问题：状态无法更新只能不断追加新副本、LTRIM 可能把它裁掉、每轮都要遍历整个 List 找最新状态。所以**独立 key 是最小且正确的做法**；同时正因为状态是从消息流水派生的，Redis 状态丢失时我们才能靠 chat_history 重建——这也是当初承诺的降级路径。

但你的第二点完全成立：**这个独立 key 不应该是为这 3 个意图定制的，而应该是通用的对话状态容器**，将来任何意图/技能都能复用。下面给出通用设计。

## 二、通用结构化对话状态设计（Schema-driven Dialogue State）

业界任务型系统（Rasa slots、Dialogflow CX session parameters、Amazon Lex session state、学术上的 Belief State）都是同一个模式：**通用的「意图 + 槽位字典」状态 + 外挂的意图 schema 注册表**。状态本身不含任何业务字段名。

### 2.1 通用状态结构

```json
{
  "version": 1,
  "sessionKey": { "userId": "u-1", "sessionId": "s-abc" },
  "status": "IDLE | ACTIVE | WAITING_SLOT | DONE | CANCELLED",

  "activeIntent": {
    "code": "order_query",
    "confidence": 0.92,
    "enteredAt": 1789000000000
  },

  "slots": {
    "orderNo": {
      "value": "SF1234567890",
      "type": "string",
      "lifecycle": "PROPOSED | CONFIRMED | VOIDED",
      "evidence": { "source": "RAW_HIT", "turn": 1, "raw": "帮我查SF1234567890" },
      "updatedAt": 1789000000000
    }
  },

  "awaiting": {
    "slot": "orderNo",
    "prompt": "请提供您的订单号（8–20 位字母或数字）",
    "retry": 0
  },

  "turn": 3,
  "intentHistory": [
    { "code": "order_query", "enteredAt": 1789000000000, "leftAt": null, "reason": "INTENT_SWITCH" }
  ],
  "attributes": { },
  "updatedAt": 1789000000000
}
```

三个关键泛化点：

1. **`slots` 是无模式字典**：任何意图的参数都是 `槽名 → 槽位信封`，新增意图不改状态结构；
2. **槽位信封统一带生命周期**：LLM 提出的值先落 `PROPOSED`，通过证据校验（RAW_HIT / CLARIFY_ANSWER / USER_UPLOAD）才升级 `CONFIRMED`，无证据或被更正则 `VOIDED`——**必填槽检查只认 CONFIRMED**，这就是"LLM 只提议、代码才裁决"在数据结构上的落点；
3. **`awaiting` 与具体槽位解耦**：ActGate 只读 `awaiting.slot` 就知道本轮输入该按哪个槽的解析器处理，不关心业务含义。

### 2.2 意图 Schema 注册表（状态之外的配置）

业务差异全部收敛到注册表，状态容器保持通用。新增意图 = 注册一份 spec（可配置化/落库），**不改状态机代码**：

```text
IntentSpec {
  code: "order_query",
  slots: {
    orderNo: { type: "string", required: true,
               validator: "orderNo",          // 指向通用校验器
               askPrompt: "请提供订单号（8–20 位字母或数字）" }
  },
  tools: ["query_order"]
}
```

三个意图在这套模型下只是三份 spec：`order_query`/`trajectory_query` 各要一个 `orderNo` 槽，`customs_generate` 要一个 `mappingExcel` 槽（type=file，validator 校验「小包号、大包号」两列）。

### 2.3 存储端口（同样通用）

```text
DialogueStateStore
  load(userId, sessionId) -> DialogueState
  save(state)                       // 带 version CAS，防并发轮次互相覆盖
  clear(userId, sessionId)
```

- Redis 实现：`wikiagent:dialogue-state:{userId}:{sessionId}` 单 key JSON，WATCH/version 乐观锁，TTL 24h；
- Redis 关闭：进程内 Map 降级；
- 状态缺失：按 §1 承诺，从 chat_history + IntentSpec 重建。

这样设计后，`wikiagent:bizstate` 就升级为**与业务无关的通用对话状态层**，本需求的 3 个意图只是它的第一批租户。

## 两处增强的依据（不是我们拍脑袋）

1. **槽位信封生命周期**：Rasa CALM 3.9 的 `from_llm` + NLUCommandAdapter 就是同一思想——LLM 提取的值必须经 mapping 裁决才发 `set slot`；Amazon Lex 有显式 `confirmationState`。我们把它做成显式状态机，与之同源。
2. **槽位证据戳 + 确定性闸**：这正是 [ReacTOD（2026）](https://arxiv.org/html/2605.19077) 的「symbolic validator 硬保证槽位合法才能结束」，也是前面召回的「Evidence-based Slot Validation」教训。属于学术/前沿生产实践，略超主流框架默认能力，但方向正确。

## 一处建议向业界对齐：状态（State）≠ 事件流水（Tracker/Checkpoint）

这是唯一需要修正的点。业界普遍把两者**分开**：

- **Rasa**：Tracker（完整事件流，可回放）由 TrackerStore 存；Slots 只是从事件流归约出的视图。
- **LangGraph**：明确区分 **Checkpointer（单会话状态快照）** 与 **Store（跨会话）**，并强调 checkpoint 与 messages 是两回事。
- 我们当前设计把「可变状态 JSON」和「可回放」都放在了同一状态对象上。

**建议**：`DialogueState`（归约态，可覆盖、可重建）只负责运行时；**可回放性由 `agent_trace` + V24 事件/工具留痕承担**（不可变事件流）。即对外仍承诺"可回放"，但回放的真相源是事件流而非那个可变 JSON。这样与 Rasa Tracker、LangGraph Checkpointer 的分层完全一致——这点我在 §1 已埋了伏笔，现在把它显式固化进设计。

## 3.3 权限与"审批"界定（需你确认的取舍）

按业界最小权限，我的建议配置：

```yaml
wikiagent:

    permissions:
      query_order:
        required-scope: order:read
        requires-approval: false      # 只读查询，免审批
      query_trajectory:
        required-scope: order:read
        requires-approval: false      # 只读查询，免审批
      generate_customs_info:
        required-scope: customs:write
        requires-approval: true       # 生成产物=写操作，执行前 TOOL_APPROVAL
    agent-allowlists:
      business-agent: [query_order, query_trajectory, generate_customs_info]
```

- **只读两个**：order:read 即可，`requires-approval=false`，不打扰用户；
- **清关生成**：定义为**写/产物操作**，需要 `customs:write` 且复用现有 `TOOL_APPROVAL` 人工门——首次执行时弹批准（同 #18 的 `toolName+args 指纹` 机制），批准才生成 Excel，驳回则 `TOOL_REJECTED_BY_USER`。这与 #14「LLM 不直接产生写副作用」一致，也避免模型一上来就批量造文件。
- 无对应 scope 的调用方：`denyReason()` 返回 `SCOPE_MISMATCH`，不执行并写 TOOL_DENIED 审计（不静默放行）。

> 说明：这里沿用现有真实生效的 `TOOL_APPROVAL` 门，而非那个未被引用的 RuleOfTwoStateMachine——与我们在对照文档里已澄清的事实保持一致。

## 4.1 复用现有 ReActExecutor，不另起循环

## 一处比业界默认更严格（有意取舍，建议保留）

Rasa CALM 的 `from_llm` **默认允许 LLM 在任意轮次直接 SetSlot**，只靠 validation 兜底；LangGraph 也信任节点内代码。而我们的闸 B **不接受没有原文/上传证据的 LLM 转述值**（"订单号是 SF123"但原文没有 → 槽位不成立）。

这比业界默认严格，属于前面确认过的**神经符号增强（ReacTOD 式证据校验）**。代价是极少数"纯指代且原文无号"场景会多问一轮；收益是杜绝模型脑补。鉴于这是你明确要的"LLM 只判不裁"，建议保留，但应在设计文档标注它是"严于业界默认"的选择。

## 一个需要写清楚的语义差异

LangGraph 的恢复是**同一 thread_id 重放 checkpoint、节点从头重跑**；我们是**新一轮 HTTP 请求 + ActGate 解析 + 复用 ReActExecutor**，并非在同一进程内续跑。

二者外部可观察行为等价（都靠持久化状态键记住位置），但有一条业界铁律我们必须照搬：**interrupt 之前若有副作用，必须幂等**（LangGraph：节点重放会重复执行 interrupt 前的代码）。对应到我们——`generate_customs_info` 落盘/写 V24 必须按 fileId 做幂等（同 fileId 重入不重复造文件、不重复建行）。这一点我会在 §5 数据模型里用唯一约束兜底。

## 5.2 表一：business_task（业务意图任务）

## 5.3 表二：business_file（文件元数据，含幂等约束）

```sql
CREATE TABLE IF NOT EXISTS business_file (
    id              BIGINT       NOT NULL AUTO_INCREMENT PRIMARY KEY,
    file_id         VARCHAR(64)  NOT NULL COMMENT '对外文件ID(bf-xxxx)',
    file_type       VARCHAR(16)  NOT NULL COMMENT 'MAPPING(上传映射表)/CUSTOMS(生成清关)',

    content_type    VARCHAR(128),
    row_count       INT          NOT NULL DEFAULT 0,
    mapping_file_id VARCHAR(64)  COMMENT 'CUSTOMS 产物:来源映射表 file_id',
    biz_task_id     VARCHAR(64)  COMMENT '软关联 business_task.biz_task_id',
    user_id         VARCHAR(64)  NOT NULL,
    checksum        VARCHAR(64)  COMMENT '文件 sha256,审计/去重',

    CONSTRAINT uk_business_file_idem UNIQUE (idempotency_key)
);
CREATE INDEX idx_business_file_task ON business_file (biz_task_id);
CREATE INDEX idx_business_file_mapping ON business_file (mapping_file_id);
```

### 幂等如何落地（兑现 §4 的 LangGraph 铁律）

关键是 `idempotency_key` 唯一约束：

- 上传映射表：`idempotency_key = file_id`；
- 生成清关：`idempotency_key = 'CUSTOMS:' + mappingFileId`。

因此**同一份映射表只会生成一份清关 Excel**：ReAct 因重放/重复提交再次进入 `generate_customs_info` 时，DB 唯一约束命中 → 直接取回已有文件记录返回，**不重复造文件、不重复建行**。这比"先查后插"更可靠（并发下由约束兜底），且 H2/MySQL 行为一致。文件物理路径用**相对路径**存储（符合你"不用绝对路径、便于部署远端"的要求），读取时由配置的 data 目录拼接。

## 必须讲清楚的一个区分：内容哈希 ≠ 操作幂等键

这两个字段回答的是不同问题，业界明确分开：

| | `checksum`（内容哈希） | `idempotency_key`（操作键） |
|---|---|---|
| 回答 | "这是不是**同一个文件内容**？" | "这是不是**同一次操作**的重试？" |
| 我们的值 | 文件 sha256 | MAPPING=file_id；CUSTOMS=`CUSTOMS:{mappingFileId}` |
| 作用 | 内容去重/防篡改 | 同一映射表只生成一份清关，重放取回旧产物 |

为什么不能合并成一个：IETF 草案规定幂等键的语义是"同一键 + 不同载荷必须拒绝"，它绑定的是**操作**而非字节内容。清关 Excel 是**生成产物**——将来若生成算法或模板改了，同一份映射表可能产出不同字节（checksum 变），但操作语义上仍应视为"这张映射表的清关已生成过"（idempotency_key 不变）。所以两者必须并存、各司其职。当前 §5 表结构已经是对的，只需在文档里写明这层区别。

## 两点可向业界再对齐（非必须，建议）

1. **同键不同载荷应拒绝而非静默返回旧结果**：Stripe/IETF 都要求同一幂等键配不同 body 时返回 422。我们的 CUSTOMS 键已绑定 mappingFileId，天然规避；但代码里命中唯一约束时，建议顺带校验入参 rows 与首次一致，不一致记冲突，避免未来踩坑。
2. **幂等键保留期约 24h~数天即可**（业界覆盖真实重试窗口即可，不必永久）；但我们的 `business_file` 同时承担"历史会话可下载"，因此**文件行要长期保留、幂等判定可独立设窗**——即文件元数据长期留，去重逻辑按需。当前 Mock 阶段保持永久即可，不额外加复杂度（YAGNI）。

## 5.3 business_file 修订

- **删除** `idempotency_key` 列（幂等语义移至上表）；
- `checksum` 保留但**不加全局唯一约束**——对标 Dropbox：物理内容可去重，但文件记录按租户独立，避免"不同用户上传同内容互相冲突"。checksum 仅用于内容审计与同用户自然去重（按 `user_id + checksum + file_type` 查）。

`business_task` 表维持上一版不变。

## 5.4 行为矩阵（Stripe / IETF 口径）

由新增的 `IdempotencyService.begin/complete/resolve` 统一裁决：

| 场景 | 判定依据 | 处理 |
|---|---|---|
| 首次请求 | insert IN_PROGRESS，唯一约束原子抢占 | 执行，完成后更新 COMPLETED + result_ref |
| 并发重复（原操作仍在跑） | 约束冲突且状态 IN_PROGRESS | **409** + `Retry-After` |
| 同键同载荷重试（已完成） | scope+key 命中且 request_hash 一致 | 不重新执行，回放 result_ref 指向的结果 |
| **同键不同载荷** | request_hash 不一致 | **422**（对齐项 1，禁止静默返回旧结果） |
| 记录已过期 | `expires_at < now` | 清理后允许重新操作 |
| 首次 FAILED | status=FAILED | 重试时复用该行重新执行 |

`request_hash` 按**归一化载荷**计算（rows/orderNo 排序后序列化的 sha256），避免字段顺序不同造成误判。

## 5.5 键与 scope 的派生规则

- **首选**：客户端 `Idempotency-Key` header——前端为一次逻辑点击（上传/生成）生成 UUID，重试或 ReAct 重放时复用；scope = `userId:endpoint/tool`；
- **未传 header 时的服务端自然键**：清关生成 = `customs:{mappingFileId}`（保证一份映射表只生成一份清关）；映射表上传无自然键，则退化为 checksum 内容去重；
- 窗口配置：`wikiagent.business-intent.idempotency-ttl-hours=24`。

## 5.6 过期清理

`@Scheduled` 每日 purge `expires_at < now` 的幂等记录（运行时遇到过期行也即时删除后重插，唯一约束仍兜底并发）。**只清幂等记录，business_file 与物理文件不动**，历史会话的下载链接长期有效。

## 5.7 实体与组件变化

- 新增：`BusinessIdempotencyEntity` + `BusinessIdempotencyRepository`（`findByScopeAndIdemKey`）、`IdempotencyService`；
- 调整：`BusinessFileEntity` 去掉 idempotencyKey 列；

# 技术设计 · §6 异常边界与降级矩阵

## 6.1 三条处理总原则（沿用现有约定）

1. **意图层失败 → 静默降级知识问答**（用户无感）；**业务执行层失败 → 显式告知/升级**（不掩盖）。分界点在"是否已确认进入业务意图"。
2. 能确定性恢复的（重试/追问）不打扰人工；**只有"连续不过闸"或"明确需要判断"才升级 human_task**，复用 [HumanRequiredException](file:///Users/huangyuan/Desktop/AI学习/wiki-Agent/src/main/java/com/wikiagent/domain/task/HumanRequiredException.java)，边界类型 HUMAN。
3. 每次异常都落 `business_task.error` + trace，**禁止吞异常静默继续**；降级/升级事件可查。

## 6.2 意图识别阶段（未进入业务前）

| 故障 | 判定 | 确定性处理 | 用户感知 |
|---|---|---|---|
| 无 API Key（NoOp 模型） | 模型空实现 | 路由 `knowledge_qa`，走现有四层链路 | 无感 |
| LLM 调用超时/5xx | 异常 | 同上降级，打点 `intent_fallback=llm_error` | 无感 |
| 返回非 JSON / 解析失败 | ParseException | 同上降级 `parse_failed` | 无感 |
| confidence < 阈值(0.8) | 校验 | 同上降级 `low_confidence` | 无感 |
| 意图名不在枚举 | 白名单校验 | 同上降级 `unknown_intent` | 无感 |
| 命中业务意图但槽位疑似 | 分类带 slots | 进业务流，槽位仍须过证据闸（不因分类值直接执行） | 正常 |

> 关键：**降级只发生在意图阶段**。一旦确认业务意图，后续失败不能再"偷偷"退回知识问答，否则用户会看到答非所问。

## 6.3 槽位收集阶段（WAITING_SLOT）

| 故障 | 处理 |
|---|---|
| 订单号格式不符（正则不过） | 不置 CONFIRMED，`slot_request` 重问并提示格式，retry+1 |
| 订单号合规但查无此单（Mock 返回未找到） | 明确告知"未查询到订单 X，请核对单号"，**允许用户改单号重试**，不转人工 |
| 用户回答连续 2 次无法解析 | retry 达上限 → `ESCALATED_HUMAN`，建 human_task |
| 上传文件非 xlsx / 缺「小包号、大包号」列 / 0 行 | 上传接口返回 422 + 具体原因（列名/空数据），前端提示重传，不占用追问次数 |
| 等待态用户说"不查了/换个问题" | ActGate 取消词 → 当前 task 置 CANCELLED，清状态，按新输入重分类 |
| 等待态用户中途改意图（高置信新意图） | 旧 task CANCELLED，新建 task（§2.5） |

## 6.4 工具执行阶段

| 故障 | ErrorCode 映射 | 处理 |
|---|---|---|
| Mock 工具确定性返回"未找到" | ——（业务结果，非异常） | 正常 Observation，Agent 据实回答 |
| 权限不足（角色/scope） | `VALIDATION_FAILED` | `TOOL_DENIED` 审计，Observation 告知无权限，不执行 |
| 幂等：并发重复 | —— | 409 + Retry-After（§5） |
| 幂等：同键异载荷 | —— | 422，拒绝 |
| Excel 生成时 POI 异常 | `INTERNAL`（可重试） | 记 FAILED，幂等行置 FAILED；下次重试重新生成 |
| 文件落盘失败（磁盘/权限） | `INTERNAL` | 同上，错误信息落 task.error；连续失败 → 提示稍后再试 |

## 建议补齐的 3 处

**1. 语义错误：先"带纠错重提示"，再决定降级（业界标准动作）**
业界对 malformed JSON / schema 违规的处理不是直接降级，而是把错误信息 append 进 prompt 再试 1 次（Re-prompt with corrective context）。我们 §6 现在 parse_failed 直接降级知识问答，偏激进——一次可自愈的格式抖动就让用户拿不到业务服务。
**建议**：意图分类解析失败时，带错误原因重试 1 次，仍失败再降级。成本仅多一次调用，命中率提升明显。

**2. 瞬态错误重试：指数退避 + 抖动**
`delay = min(base × 2^attempt + random_jitter, max_delay)`，业界称黄金标准，专门防止多个请求同时重试打爆服务。
**建议**：对 timeout/5xx 的重试明确用此策略（base=1s，max=60s，最多 2–3 次）。Mock 阶段外部依赖少，但 LLM API 是真实的，值得加。

**3. 熔断器：连续失败快速失败**
某一类调用（如分类 LLM）连续 N 次失败，熔断器 open，后续请求**立即降级**不再等待，冷却后半开探测。业界强调"没有熔断器的多 Agent 是指向自己基础设施的 DDoS"。
**建议**：给意图分类调用加一个轻量熔断器（失败阈值 5 次、冷却 30s）。这是纯后端小组件。

# §6 修订版：异常边界、降级矩阵与弹性机制

## 6.1 处理总原则

1. **错误分类先行（Classify before retry）**：任何失败先归入四类，再决定动作——
   - **瞬态 Transient**（超时/5xx/网络抖动）→ 退避重试；
   - **语义 Semantic**（JSON 畸形/schema 违规/工具名臆造）→ 带纠错上下文重提示；
   - **资源 Resource**（预算耗尽/上下文溢出）→ 裁剪或收口；
   - **致命 Fatal**（401/403/无 Key）→ 不重试，降级或标记。
2. **意图层失败静默降级知识问答；业务执行层失败显式告知/升级**，分界点是"是否已确认进入业务意图"。
3. 能确定性恢复的不打扰人工；**连续不过闸才升级 human_task**，复用 HumanRequiredException（HUMAN 边界）。
4. 每次异常落 `business_task.error` + trace，**禁止吞异常静默继续**。

## 6.2 三个弹性组件（新增，业界标配）

### 组件一：指数退避 + 抖动（瞬态错误）

```text
delay = min(base × 2^attempt + random(0, base), maxDelay)
base=1s，maxDelay=60s，最多重试 2–3 次
```
适用于 LLM 调用超时/5xx。抖动防止多请求同时重试形成惊群。429 限流不按退避重打同一模型，直接进入降级；401/403/无 Key 完全不重试。

### 组件二：带纠错上下文的重提示（语义错误）

意图分类返回非 JSON / schema 不符时，**不立即降级**：
```text
第 1 次解析失败 → 把解析错误原因 append 进 prompt，重提示 1 次
仍失败        → 才走降级知识问答
```
让一次可自愈的格式抖动不至于让用户丢掉业务服务。工具执行阶段的参数错误同理，Observation 回告明确错误，由 ReAct 自愈。

### 组件三：熔断器 Circuit Breaker（连续失败快速失败）

对意图分类 LLM 调用加轻量熔断器：
```text
CLOSED：连续失败达阈值(默认 5 次) → OPEN
OPEN：后续请求立即降级，不再等待 LLM；冷却 30s → HALF_OPEN
HALF_OPEN：放 1 个探测请求，成功 → CLOSED，失败 → 回 OPEN
```
避免上游持续故障时反复等待、放大负载。熔断状态变更打点可查。

## 6.3 意图识别阶段（未进入业务前）

| 故障 | 类别 | 确定性处理 | 用户感知 |
|---|---|---|---|
| 无 API Key（NoOp 模型） | Fatal | 路由 knowledge_qa，走现有四层链路 | 无感 |
| 401/403 | Fatal | 不重试，降级并标记 | 无感 |
| 超时/5xx/网络错误 | Transient | 退避+抖动重试 2 次，仍失败则降级 | 一般无感 |
| 非 JSON / schema 不符 | Semantic | **带纠错重提示 1 次**，仍失败降级 `parse_failed` | 一般无感 |
