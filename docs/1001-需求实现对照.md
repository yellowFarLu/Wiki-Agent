## 1. 可靠的任务与数据链

**现状：已实现。** 排队、并发、重复提交、超时、重试、取消、恢复、人工接管八个能力全部落在通用任务框架。

**方案**：MySQL 状态机是唯一真相源，RocketMQ 负责投递，Redis 负责协调（租约标志/锁）。任务经历 `PENDING → DISPATCH → RUNNING → 终态（COMPLETED/FAILED/CANCELLED）`，另有 TIMEOUT / WAITING_HUMAN / SUSPENDED 中间态。

| 能力 | 机制 |
|---|---|
| 排队 | PENDING 落库后投递；滞留 PENDING 由 `DispatchCompensationJob` 每 5s 扫描补偿；RocketMQ Tag 区分 INGEST/AGENT 独立消费组（并发度 ingest=2 / agent=4） |
| 并发 | Worker 以 CAS 抢租约（PENDING/DISPATCH + 无主或租约过期）；控制命令 version CAS 防并发冲突 |
| 重复提交 | `task_instance.biz_key` 唯一约束幂等；提交时先查已有条目，重复上传直接返回既有 taskId |
| 超时 | 步骤边界检查 deadlineSec；`TaskWatchdog` 看门狗处理整体 deadline（默认 1800s）；单步超时 300s、Agent 步骤 180s；到点置 TIMEOUT 并走重试 |
| 重试 | `attempt` 字段控制，指数退避 10s→30s→2min，最多 3 次；`ErrorClassifier` 区分可重试/致命错误（致命不重试） |
| 取消 | `TaskControlService` 的 suspend/resume/cancel 双写 MySQL+Redis，version CAS 校验（冲突抛 `OptimisticControlConflictException`） |
| 恢复 | `TaskRecoveryJob` 每 15s 扫描过期租约（TTL 30s）重投；步骤级 Checkpoint：DONE 步骤不重跑，动态注册步骤先 `mergeRegistered` 合并；心跳续租要求 owner+RUNNING 双条件，防误杀健康长任务 |
| 人工接管 | `WAITING_HUMAN` 态 + `human_task` 表：INPUT（补充信息后从 Checkpoint 续跑）/ DIRECT_RESOLVE（人工直接终结）；人工任务复用 pending 单幂等防重复建单 |

**技术选型**：MySQL 8（状态机）+ RocketMQ 5.3.1（Tag 分类、延迟消息适配退避）+ Redis/Redisson（租约/锁）。降级约定：RocketMQ 不可用 → JVM 本地调度；Redis 不可用 → MySQL 行字段；MySQL 不可用 → 拒绝启动（防静默丢任务）。

**系统链路**

```text
【提交链路】
DocumentController / 上传入口
  → TaskSubmissionService：bizKey 查重 → task_instance 落库 PENDING（唯一约束兜底并发幂等）
  → TaskMessageSink 投递：TASK_MQ=rocketmq（Tag=INGEST/AGENT，独立消费组）｜=local（JVM 调度兜底）
  → TaskWorker CAS 抢租约（PENDING/DISPATCH + 无主或租约过期）→ DISPATCH → RUNNING
  → TaskHandlerRegistry 找 handler → 逐步推进，每步 Checkpoint 落 task_step
  → TaskStreamBus → BusSseSender → SSE progress 推前端（TaskQueryService 轮询兜底）
  → 终态 COMPLETED ｜ FAILED（attempt≤3 退避重投）｜ CANCELLED

【自愈链路】
Worker 心跳 10s 续租（owner+RUNNING 双条件，防误杀健康长任务）
TaskRecoveryJob 15s 扫过期租约（TTL 30s）→ 重投 → 新 Worker mergeRegistered 合并动态步骤 → 已 DONE 不重跑
DispatchCompensationJob 5s 捞滞留 PENDING ｜ TaskWatchdog 扫 deadline 到点 → TIMEOUT → 走重试
执行中发现租约丢失 → 抛 LeaseLostSignalException 主动让出，不产生双写

【控制链路】
前端按钮 → TaskControlService（suspend/resume/cancel）→ 双写 MySQL 状态 + Redis 标志（version CAS，冲突抛 OptimisticControlConflictException）
→ Worker 在步骤/ReAct 循环边界读到标志 → 暂停让出 ｜ 恢复续跑 ｜ 取消置终态

【人工接管链路】
步骤抛 HumanRequiredException（加密 PDF 要密码 / 预算超限 / Agent 等输入）
→ 状态 WAITING_HUMAN + human_task 落库（INPUT/DIRECT_RESOLVE 两类，复用 pending 单幂等）
→ 人工工作台认领 → INPUT 补充信息（从 Checkpoint 断点续跑）｜ DIRECT_RESOLVE 人工结论直接终结
```

## 2. 文件上传与多格式解析

**现状：已实现；「超大文件」未见专门分片/限流设计，靠单步超时（300s）与任务 deadline 兜底。**

**方案**：上传即建任务（同步返回 taskId，解析异步执行），六步流水线 `PARSING → CLEANING → CHUNKING → EMBEDDING → INDEXING → READY`（可选 EXTRACTING），每步更新文档状态并做终态校验。

| 需求点 | 实现 |
|---|---|
| 文件上传 | `POST /api/documents`（multipart，带 effectiveDate），`ParseInputValidator.DocKind` 分流六类介质 |
| 语音转写 | paraformer-v2 ASR（wav/m4a/aac），超时 120s |
| OCR | 图片走 qwen-vl-plus 视觉模型；PDF 文本层 <20 字符的页 144dpi 栅格化后 OCR |
| 版面/表格解析 | DashScope DocAI，经 `DocumentAiGateway` Capability 探测调用（版面 30s/表格 60s，重试 3 次，连续 3 次失败熔断 60s） |
| 复杂 PDF | PDFBox 3.0.8 逐页抽取；文本层疑似 cmap 乱码时 OCR 双跑差异比对 |
| 跨页表格 | [TableStitcher.java](../src/main/java/com/wikiagent/application/parse/TableStitcher.java) 缝合后再切分 |
| 扫描件 | 全扫描件 → OCR 路径；供应商未配置/熔断 → `aiSkipped=true` 终态 AI_SKIPPED，不产出空 chunk |
| 加密文件 | 抛 `EncryptedDocumentException` → 建 **DECRYPT 人工任务**等密码后继续 |
| 损坏文件 | `IllegalStateException` 归类 PARSE_FAILED，**致命不重试**（不静默吞错） |
| 结构化提取 | [FieldExtractionService.java](../src/main/java/com/wikiagent/application/extract/FieldExtractionService.java)：schema 注册 → 提示词 → LLM JSON → 逐字段类型/枚举校验（schema 外字段拒绝并登记） |
| 字段校验/低置信 | 置信度默认 <0.75 进修复重抽（最多 1 轮），产出 ExtractionReport（schema key/version + accepted + errors） |
| 去重 | 子块 content_hash（V19）精确去重 + MinHash-LSH 近重复检测（见 #4/#12） |
| 失败重跑 | 任务框架重试机制（#1）+ 任务详情页重放按钮 |

**技术选型**：PDFBox 3.0.8 + Apache POI 5.5.1（docx/xlsx）+ Tika 3.3.2（旧格式）本地解析兜底；DashScope 多模态云端增强；`wikiagent.parse.provider=none/dashscope` 开关。

**系统链路**

```text
UploadPanel 拖拽 → POST /api/documents（multipart + domain/subDomain/effectiveDate + 身份头）
→ DocumentController：bizKey/内容查重（重复 → 直接返回既有 taskId，duplicate=true）
→ 建 INGEST 任务（#1 链路）→ IngestTaskHandler 步进六步流水线：

 ① PARSING   RichDocumentParser → ParseInputValidator.DocKind 分流：
             PDF：PDFBox 逐页文本层；页文本<20 字符 → 144dpi 栅格化 → OCR；疑似 cmap 乱码 → OCR 双跑差异比对
             IMAGE → qwen-vl-plus 视觉 OCR ｜ AUDIO → paraformer-v2 ASR
             版面/表格 → DocumentAiGateway（Capability 探测，超时 30/120/30/60s，重试 3，熔断 60s）
             加密 PDF → EncryptedDocumentException → DECRYPT 人工任务等密码后继续
             损坏 → PARSE_FAILED 致命不重试 ｜ AI 不可用 → aiSkipped=true 终态 AI_SKIPPED 不产空 chunk
 ② CLEANING  TextCleaner：控制字符/合并空白/页眉页脚噪声
 ③ CHUNKING  ChunkSplitter 父子切分（父 1000/子 350 token，递归边界回退；跨页表格先经 TableStitcher 缝合）
 ④ EMBEDDING text-embedding-v4 批量 10（缓存命中跳过重复计费）
 ⑤ INDEXING  ContentHasher 算 content_hash → MilvusStoreService 写子块（向量+BM25+标量）；父子全文落 MySQL
 ⑥ READY     触发可选后置：GraphRAG 实体关系抽取 / 结构化字段抽取（异步，单 chunk 失败只告警不阻断）

每步更新文档状态并 SSE 推进度；任一步失败 → FAILED + error 留痕 → 任务详情可重放
```

**代码位置**：[IngestionService.java](../src/main/java/com/wikiagent/service/ingest/IngestionService.java) · [RichDocumentParser.java](../src/main/java/com/wikiagent/application/parse/RichDocumentParser.java) · [ParseInputValidator.java](../src/main/java/com/wikiagent/application/parse/ParseInputValidator.java) · [DocumentAiGateway.java](../src/main/java/com/wikiagent/application/parse/DocumentAiGateway.java) · [TextCleaner.java](../src/main/java/com/wikiagent/service/ingest/TextCleaner.java)；设计文档 [ingestion.md](ingestion.md)

## 3. 血缘与版本（材料↔解析↔模型↔人工的关系）

**现状：已实现。** 关键字段和结论可定位到文件、页码、原文片段、知识版本、业务规则。

**方案**：`ProvenanceService` 维护「文档 → 制品/字段 → chunk → 版本」全链路溯源，血缘有向边（来源 → 派生）落库：

| 表（V10–V12） | 用途 |
|---|---|
| `doc_artifact` | 文档级制品（V11 起 chunk 经 artifact_id 挂接） |
| `provenance_edge` | 血缘有向边 |
| `extracted_field` | 结构化抽取字段实例 |
| `field_version` | 字段版本（值变更可追溯） |
| `doc_version` | 文档版本 |

- **页码**：`IngestionService.mapToPageNo` 按文本匹配把子块映射到解析页，页号存子块元数据；
- **原文片段**：答案引用 `Source` 六字段 `docId / versionNo / pageNo / snippet（代表子块前 200 字符）/ artifactId / score`；
- **知识版本**：doc_version + 生效日期（V19 effectiveDate，上传时确认，作为去重/冲突裁决时效依据）；
- **业务规则**：规则执行留痕 `rule_computation`（见 #6）；冲突裁决给 `resolution_hint`；
- **前端**：字段血缘抽屉 [FieldLineageDrawer.tsx](../frontend/components/results/FieldLineageDrawer.tsx)、版本 diff [VersionHistoryTab.tsx](../frontend/components/workbench/VersionHistoryTab.tsx)。

**系统链路**

```text
【写入侧（随入库/抽取/修改逐步生成血缘）】
上传：domain/身份标签 + effectiveDate → knowledge_metadata 打标
解析：mapToPageNo 按文本匹配把 chunk 映射到页号（页号存子块元数据）
索引：chunk 经 artifact_id 挂接 doc_artifact；provenance_edge 记"来源 → 派生"有向边
抽取：字段实例落 extracted_field；人工/重抽修改落 field_version（值变更链，不覆盖旧值）
更新：doc_version 新版本 + effectiveDate 留存；冲突裁决结果落 conflict_resolution（source/resolution_hint）
规则：确定性计算落 rule_computation（输入快照/规则版本/输出）——业务规则可定位

【读取侧（从答案反查回原始材料）】
问答命中子块 → RetrievalService 选代表子块（父块下最高分，平局取 childIndex 最小）
→ 回填 Source 六字段（docId/versionNo/pageNo/snippet/artifactId/score）
→ SSE sources 事件 → 前端引用角标
→ 用户点开：来源详情（定位文件+页码+原文片段）｜ FieldLineageDrawer 按字段反查
   字段 → chunk → 制品 → 文档 → 版本（沿 provenance_edge 逐级回溯）
```

**代码位置**：[ProvenanceService.java](../src/main/java/com/wikiagent/application/lineage/ProvenanceService.java)；迁移 V10/V11/V12/V19；设计文档 [governance.md §2](governance.md)

## 4. RAG 与模型接入

**现状：已实现；供应商切换有 Provider 抽象与降级链，但生产主要接 DashScope 一家（诚实话）。**

### RAG 侧

| 需求点 | 实现 |
|---|---|
| 清洗 | [TextCleaner.java](../src/main/java/com/wikiagent/service/ingest/TextCleaner.java)：去控制字符、合并空白、去页眉页脚 |
| 切分 | [ChunkSplitter.java](../src/main/java/com/wikiagent/service/ingest/ChunkSplitter.java)：父子两级 small-to-big，父 1000 / 子 350 token，递归边界回退（标题→围栏→段落→行→句读→空格→单字符） |
| 元数据 | `knowledge_metadata`（V11）、`kb_child_chunk`（content_hash、页号、父块 id、域/身份标签） |
| 权限过滤 | `RetrievalFilter` + `RetrievalSecurityContext`：身份/业务域标签在 **Milvus 标量过滤层**排除越权内容（9 域 × 6 子域 × 5 身份） |
| 关键词+向量检索 | Milvus 2.5 服务端混合检索：Dense（text-embedding-v4，1024 维）+ BM25（k1=1.2, b=0.75），**服务端 RRF 融合 k=60**，多查询扩展并行召回 |
| 重排 | gte-rerank 精排 topK=10；灰度门控（GrayReleaseService），失败/未放量保持原序不阻断 |
| 引用 | Source 六字段（#3）；答案附引用角标 + traceId，SSE `sources` 事件 |
| 更新/删除 | 文档版本替换（doc_version）；Milvus 不支持 chunk 级物理删除 → `is_active` 软删；冲突裁决到 chunk 级而非整文档 |
| 评测 | 7 项自研指标 + RAGAS 6 指标（见 #8） |

检索期两道守卫（默认开启）：近重复去重（near-jaccard 0.9）、冲突守卫（coarse-cosine 0.85 粗筛 → LLM 精判 0.8，冲突 KEPT_BOTH 双保留打标注，不静默二选一）。Milvus 故障 → 60s 熔断冷却 + 中文 bigram 关键词本地降级（查 MySQL 子块表）。

```text
→ SSE：stage → sources → delta（流式）→ done；答案附引用角标 + traceId

【Prompt/缓存链路】
调用前 PromptTemplateService 按 code 取 ACTIVE 版模板（code+version 唯一）→ 渲染占位符 → ProviderChain
embedding 缓存 TTL 86400s；答案缓存默认关（防幻觉）
```

## 6. 确定性规则与计算模块 + 人工复核

**现状：已实现。**

**方案**（V13 规则引擎）：

```text

```

| 需求点 | 实现 |
|---|---|
| 完整保存输入/规则版本/过程/输出 | `rule_computation` 表留痕，支持重新计算与回放 |
| 重算/回放 | 规则计算按留痕重算；任务级重放（任务详情 replay，已 DONE 步骤不重跑） |

| 版本差异 | doc_version + 前端 VersionHistoryTab diff 视图 |
| 通过/驳回 | [ReviewCasesTab.tsx](../frontend/components/workbench/ReviewCasesTab.tsx) approve/reject 操作 |
| 操作留痕 | `audit_log`（V3）+ 网关审计（V8）+ trace_id（V16）贯通 |

**设计原则（面试重点）**：规则是确定性程序——同样输入 + 同样规则版本必得同样输出，因此可回放、可审计；LLM 只负责检测/提取类判断，**不做裁决**（见 #14）。

**系统链路**

```text
【规则定义链路】
业务规则文本（DSL）→ RuleDslParser 解析校验 → RuleSetService 版本化管理 rule_set（规则变更=新版本，不改历史）

【规则执行链路（确定性）】
业务输入 + 指定规则版本 → RuleExecutionService 执行
→ 全程留痕 rule_computation（输入快照/规则版本/中间过程/输出）
→ 同输入 + 同版本必同输出 → 支持重算与回放（任务详情 replay，已 DONE 步骤不重跑）

【人工复核链路】
执行命中存疑/例外 → ReviewCaseService 建 review_case
→ 人工工作台 ReviewCasesTab 认领 → 材料对照（原文/抽取字段/规则结论并排）
→ 字段修改 → 落 field_version 新版本（旧值保留可 diff）
→ approve（确认生效）/ reject（驳回重抽/重算）→ 结论留痕 audit_log（V3）+ trace_id（V16）贯通
```

## 14. 模型判断 / 确定性规则 / 人工判断 三分离

**现状：已实现，且有一条明确的设计原则贯穿。**

| 判断类型 | 承担方 | 留痕/回放方式 |
|---|---|---|
| 模型判断 | LLM 路由、字段抽取、冲突初判、答案裁判、RAGAS judge | model_call_log（含 prompt 模板版本）；agent_trace |
| 确定性规则 | 规则引擎（DSL 解析+执行）、content_hash 精确去重、MinHash+KeyTokenDiffer 粗筛、effective_date 时效裁决、StaleScore | rule_computation（输入+规则版本+输出）→ 可重算可回放 |
| 人工判断 | review_case 通过/驳回、human_task 补充/直接终结、同日期冲突人工仲裁、RAGAS 样本审核 | audit_log + 字段版本 field_version + 任务事件流水 |

**核心原则（面试金句）**：**LLM 只检测、不裁决**。冲突判定 LLM 只返回结构化 JSON（conflict pairs），裁决交给确定性规则（effective_date 新者胜）+ 人工仲裁兜底（生效日期相同/缺失时不自动二选一，双保留打标注）；规则引擎是纯确定性程序——同输入+同规则版本必同输出，因此可重算、可回放、可审计；所有三类判断都落库留痕，结论可经血缘（#3）追溯。

**系统链路**

```text
以「跨文档冲突」一条链路看三种判断如何分工：

 ① 模型判断（只检测，不裁决）
入库后 ConflictDetectionService 批量扫同主题
→ 确定性粗筛：cosine ≥0.85 + KeyTokenDiffer 关键 token diff（数字/日期/否定 vs 措辞/标点）
→ 命中候选 → ConflictLlmJudge（qwen-flash）输出结构化 JSON（是否冲突 + 冲突对）——到此为止，不做取舍

 ② 确定性规则（裁决）
ConflictResolutionService 按 effective_date 新者胜，chunk 级去留（非整文档）
→ 结果 + resolution_hint 落 conflict_resolution
→ 同输入同裁决口径必同结果 → 可重算、可回放

 ③ 人工判断（兜底）
生效日期相同/缺失 → 不自动二选一 → 双保留 + conflict 标注进上下文
→ ConflictReviewPanel 人工仲裁 → 结论落 conflict_resolution（留痕 audit_log）
同理：review_case 通过/驳回、human_task 补充/终结、RAGAS 样本 approve/reject 都是人工判断域

【边界划分总链路】
固定流程（确定性程序）= ChatService 第 4 层简单 RAG 管道（改写→检索→生成）
Agent（模型判断）= PERO/多 Agent（wikiagent.pero.enabled 分层开关切换）
专业人员 = 人工工作台（复核/接管）
追溯：三类判断结论都可沿 provenance_edge / rule_computation / audit_log / trace_id 回放到具体输入与版本
```

**代码位置**：规则引擎 [application/rule/](../src/main/java/com/wikiagent/application/rule/RuleExecutionService.java)；冲突治理 [ConflictResolutionService.java](../src/main/java/com/wikiagent/application/knowledge/ConflictResolutionService.java) + [ConflictLlmJudge.java](../src/main/java/com/wikiagent/service/retrieve/ConflictLlmJudge.java)；设计文档 [governance.md](governance.md)

## 16. 记忆体系迁移到 Redis / Milvus / MySQL

**现状：已实现。** 短期/长期记忆不再依赖本地文件，端口定义在 `domain/memory`，五个可插拔适配器在 [infrastructure/memory/](../src/main/java/com/wikiagent/infrastructure/memory)（redis/mysql/milvus/inmemory/file）。

| 层 | 存储 | 规则 |
|---|---|---|
| 短期记忆 | **Redis**（关闭时 inmemory 兜底） | 每会话 ≤20 轮、TTL 24h；key 以 sessionId+userId 前缀隔离 |
| 用户画像 | **MySQL**（userId 主键） | 稳定偏好/背景；由 UpdateUserProfileTool 经规则之双审批写入 |
| 历史事件（长期情景记忆） | **Milvus**（父子索引） | `is_active` 软删除，检索可过滤 |
| 交接清单 | **MySQL**（默认 `handover-adapter=mysql`） | 主表/节点/数据引用/放弃路径四表；另有 file 适配器 + 一次性迁移开关 |

**系统链路**

```text
【读链路（Perception 拉取上下文）】
请求（sessionId + userId）→ SimplePerception 并行拉四层：
 短期记忆  Redis（key = sessionId+userId 前缀隔离；≤20 轮环形、TTL 24h；redis.enabled=false → inmemory 兜底）
 用户画像  MySQL（userId 主键查稳定偏好/背景）
 历史事件  Milvus 向量检索（is_active=true 过滤；Milvus 挂 → 熔断降级不阻塞主流程）
 交接清单  MySQL 四表（上次会话的原始请求/已执行节点/放弃路径/数据引用）
→ 汇总注入 Plan / Execute 上下文

【写链路（Optimize 沉淀 + 工具写入）】
Optimize(SimpleOptimizer) 经验 → MilvusEventSink 写历史事件库（is_active 软删，可检索可过滤）
交接清单 → MemoryHandover 实时 write-through HandoverRepository（线程安全单例，读写分离一致）
用户画像 → UpdateUserProfileTool → RuleOfTwo 审批通过 → 才落 MySQL（Agent 不能自行写画像）

【适配与隔离】
domain/memory 四端口 → infrastructure/memory 五实现（redis/mysql/milvus/inmemory/file）依赖倒置
handover-adapter=mysql 默认（file 适配器 + file-migration.enabled 一次性迁移，替代旧 todo.json/本地文件）
TenantKey（域+子域+身份）→ 跨租户记忆与知识不串
```
