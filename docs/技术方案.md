# 企业知识库（wiki-Agent）技术方案

> 版本：v1.1 ｜ 日期：2026-09-19
> 所有依赖版本与 API 用法均已通过 Maven Central 官方仓库、Milvus Java SDK 源码、官方文档逐一核实，无凭记忆填写的内容。

## 1. 需求回顾

构建一个可本地运行的企业知识库问答系统（RAG），完整链路：

1. **入库**：文档清洗 → 切分为 chunk → 构建父子索引 → chunk 向量化 → 写入向量数据库
2. **检索**：查询改写 → BM25 + 向量双路召回 → 倒排融合 + RRF → top10 chunk
3. **生成**：top10 子切片替换为父文档 → 组装 Prompt → 提交大模型（流式）
4. **输出**：大模型基于上下文总结作答
5. **交付**：可运行前端页面 + 本地后端服务，SSE 流式传输

技术栈约束（用户已确认）：Spring AI Alibaba 框架、DashScope 接入 LLM 与 Embedding、远程 Milvus（≥2.5）作为向量库且 **BM25 使用 Milvus 内置全文检索**，支持 TXT/Markdown/PDF/Word/Excel。

### BM25 选型说明（用户已确认方案 B）

BM25 由 **Milvus 内置全文检索**（Milvus 2.5+ 特性）承担，不再使用本地 Lucene：

- **入库时**：子块文本写入 Milvus 的 `text` 字段（VarChar，`enable_analyzer=true`，中文 analyzer），Milvus 服务端通过内置 `FunctionType.BM25` 函数自动生成稀疏向量存入 `sparse` 字段——无需客户端计算稀疏向量
- **检索时**：一次 `hybridSearch` 同时携带 dense 查询向量（`FloatVec`）与原始查询文本（`EmbeddedText`，服务端做 BM25 向量化），服务端完成倒排检索 + RRF 融合
- 依据：Milvus 官方文档 Full Text Search（Java 示例）+ milvus-sdk-java 2.5.17 源码（`CreateCollectionReq.Function`、`FieldSchema.enableAnalyzer/analyzerParams`、`EmbeddedText`、`HybridSearchReq`/`AnnSearchReq`/`RRFRanker` 均已逐一确认存在）
- **兜底方案**：若联调发现用户的 Milvus 服务端实际版本 < 2.5 或不支持该特性，回退本地 Lucene 10.5.1 BM25（方案 A，实现约 2 个类的代价），接口层不受影响

### 关键配置（application.yml）

```yaml
spring:
  ai:
    dashscope:
      api-key: ${DASHSCOPE_API_KEY}          # 环境变量注入，不落盘
      chat:
        options:
          model: qwen-plus
      embedding:
        options:
          model: text-embedding-v4
          dimensions: 1024                   # text-embedding-v4 默认即 1024

wikiagent:                                   # 本项目自定义配置
  milvus:
    uri: http://${MILVUS_HOST}:${MILVUS_PORT:19530}
    username: ${MILVUS_USERNAME:root}
    password: ${MILVUS_PASSWORD:milvus}
    collection: wikiagent_chunks
    dimension: 1024
    bm25-k1: 1.2                             # Milvus BM25 参数（官方默认）
    bm25-b: 0.75
  retrieve:
    sub-topk: 20                             # 每路召回数
    final-topk: 10                           # RRF 融合后子块数（用户流程指定 top10）
    rrf-k: 60
    parent-char-budget: 12000                # 父文档总字符预算
  ingest:
    parent-size: 1000                        # 父块目标长度（token，选型依据见 docs/ingestion.md §2.1）
    parent-overlap: 150
    child-size: 350                          # 子块目标长度（token，选型依据见 docs/ingestion.md §2.1）
    child-overlap: 60
```

## 4. 数据模型与父子索引设计

### 4.1 切分策略

- **父块（parent）**：1000 token（QwenStyleTokenEstimator 口径，中文约 1 字=1 token），重叠 150，按 Markdown 标题/代码围栏/段落/行/中英文句读递归边界优先切分 —— 用于最终提供给 LLM 的上下文（选型依据见 [docs/ingestion.md §2.1](ingestion.md)）
- **子块（child）**：350 token，重叠 60，在父块内部切分 —— 用于双路检索（短块语义更聚焦，召回更准）
- 关系：`child.parent_id → parent.id`，一个父块含 1~N 个子块

### 4.2 存储分工

| 存储 | 内容 | 说明 |
|---|---|---|
| Milvus（远程） | collection `wikiagent_chunks`：子块 dense 向量 + **BM25 稀疏向量（服务端自动生成）** + 子块文本 + 元数据 | 命中子块后凭 parent_id 回查 H2 取父块 |
| H2（本地 `./data/h2/kb.mv.db`） | 文档表、父块表（全文）、子块表（全文） | 事实源；支撑父文档替换、删除、Milvus 重建 |
| 本地 `./data/uploads/` | 原始上传文件留档 | |

### 4.3 Milvus collection schema（SDK 源码已核实对应 API）

```
id          VarChar(64)   主键（= 子块 UUID）
text        VarChar(65535) enable_analyzer=true, analyzer_params={"type":"chinese"}   ← 中文 jieba 分词
sparse      SparseFloatVector                        ← BM25 Function 自动生成，不可手动写入
dense       FloatVector(1024)                        ← DashScope text-embedding-v4
doc_id      VarChar(64)   标量
parent_id   VarChar(64)   标量
child_index Int32         标量

Function: name="text_bm25_emb", type=BM25, input=["text"], output=["sparse"]
索引: sparse → SPARSE_INVERTED_INDEX(metric=BM25, bm25_k1, bm25_b)
      dense  → HNSW(metric=COSINE)
```

### 4.4 H2 表结构

- `kb_document`：id, filename, doc_type, size_bytes, status, chunk_count, error, created_at
  - status：`PARSING → CLEANING → CHUNKING → EMBEDDING → INDEXING → READY / FAILED`
- `kb_parent_chunk`：id, doc_id, parent_index, content
- `kb_child_chunk`：id, doc_id, parent_id, child_index, content

## 5. 检索与生成链路（核心流程）

```
用户问题
   │
   ▼
① 查询改写（LLM, qwen-plus, temperature=0.1）
   消解指代、补全省略，输出一句适合检索的独立问题；LLM 失败时回退原始 query
   │
   ▼
② 用改写后的 query 调 DashScope embedding → dense 查询向量（1024 维）
   │
   ▼
③ Milvus hybridSearch（一次请求，服务端双路召回+倒排融合）：
   ├─ AnnSearchReq#1  vectorFieldName=dense   vectors=[FloatVec(query向量)]  topK=20
   ├─ AnnSearchReq#2  vectorFieldName=sparse  vectors=[EmbeddedText(query)]  topK=20
   └─ ranker = RRFRanker(k=60)  →  limit = 10  →  top10 子块（含 RRF 融合分）
   │
   ▼
④ 父文档替换：top10 子块 → parent_id 去重 → 按最优 RRF 排名降序取父块（字符预算 12000）
   │
   ▼
⑤ Prompt 组装：
   System：企业知识库助手角色 + 引用规范（仅依据材料回答；材料不足时明确说明，不编造）
   User：<context> 中按 [1][2]… 编号嵌入父块（含来源文件名）+ 用户问题
   │
   ▼
⑥ ChatClient.stream() 流式生成 → SSE 推送前端
```

### 5.1 SSE 事件协议（`POST /api/chat`，`text/event-stream`）

| event | data | 说明 |
|---|---|---|
| `stage` | `{"step":"rewrite","query":"..."}` | 查询改写结果 |
| `stage` | `{"step":"retrieve","children":10,"parents":6}` | 融合后子块数与父块数 |
| `sources` | `[{"no":1,"docName":"xx.pdf","parentIndex":3,"score":0.0325}]` | 引用来源（生成前推送） |
| `delta` | `{"text":"..."}` | LLM 增量 token |
| `done` | `{}` | 结束 |
| `error` | `{"message":"..."}` | 异常 |

> 注：RRF 融合在 Milvus 服务端完成，因此 BM25 与向量两路的中间命中数不再分开发布（服务端只返回融合结果），前端展示融合后数量与引用来源。
> 前端用 `fetch` + `ReadableStream` 手工解析 SSE 帧（EventSource 仅支持 GET，无法携带 JSON 请求体）。

## 9. 边界与风险（如实说明）

1. **端到端验证依赖真实凭据**：没有 DashScope API Key 与可连通的 Milvus 之前，只能完成编译、单元测试（切分/清洗/Prompt 组装等纯逻辑）与应用启动校验，无法验证检索与生成效果。
2. **EmbeddedText 查询机制需联调确认**：`EmbeddedText`（查询文本服务端向量化）已从 milvus-sdk-java 2.5.17 源码确认存在，但实际行为取决于你的 Milvus 服务端版本；联调时若服务端不支持，回退 Lucene 方案 A。
3. **旧版二进制格式不支持**：`.doc`/`.xls` 不解析，上传时明确报错；支持 `.docx`/`.xlsx`/`.pdf`/`.txt`/`.md`。
4. **Excel 语义局限**：按行转"列1 | 列2 | …"文本，复杂合并单元格/公式场景效果有限。
5. **Embedding 批量限制**：text-embedding-v4 单次请求最多 10 条文本，入库按 10 条/批分批调用。
6. **collection 冲突**：若 `wikiagent_chunks` 已存在但 schema 不符，启动自检会明确报错提示，不会静默覆盖。
7. **检索参数可调**：双路各召回 20、RRF k=60、最终 top10、父块字符预算 12000，集中在配置文件。
